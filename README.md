# 성경 근거 설교 작성기 · LM Studio Edition V40

주제, 세부사항, 중심본문을 입력하면 로컬 LM Studio 모델이 등록된 성경 자료와 교리 문서를 근거로 설교 초안을 만드는 Windows용 V40입니다. OpenAI API 키는 필요하지 않습니다.

## V40.9.1 · Qwen 추론 전용 응답 수정

- Qwen 27B가 3대지 구조 생성에서 내부 reasoning 토큰만 쓰고 최종 본문을 내기 전에 1,400토큰 제한에 도달하던 문제를 수정했습니다.
- 3대지 생성의 인위적 출력 제한을 제거하고 스트리밍 연결이 유지되는 동안 최종 JSON 본문을 기다립니다.
- reasoning 스트림과 최종 content 스트림을 구분하고, 최종 답변이 없으면 모델 Thinking 설정을 확인하도록 정확히 안내합니다.

## V40.2 · 영어 번역본 3군 정책과 표현 보조 안전장치

FIXED9은 영어 번역본을 많이 넣는 대신 역할에 따라 제한합니다. **1군 핵심 엔진**은 ESV·NASB·NIV·CSB·NET, **2군 전문 연구 확장**은 NRSVue·NKJV·NLT, **3군 비교·교육 보조**는 KJV·GNT·CEV·AMP·The Message입니다. 실제 핵심 엔진 준비상태는 `개역개정 + 히브리어/헬라어 원문 + ESV + NASB + NIV + CSB + NET`을 기준으로 대시보드에 표시하지만, 미등록 항목은 저작권 자료를 추측하지 않고 권장 보완으로만 안내합니다.

AMP와 The Message는 표현을 이해하기 위한 보조자료로만 전달되며 원어 의미·교리적 결론·번역 쟁점의 증거로 사용할 수 없습니다. 3군 자료가 핵심 엔진과 충돌하면 등록된 개역개정·원문·1군 번역을 우선합니다. 또한 영어 `GNT`를 헬라어 원문으로 잘못 분류하지 않도록 언어 코드를 함께 검사하고, `NET 본문`과 `NET Notes`도 구분하여 주석 파일만으로 NET 본문 준비가 통과되지 않게 했습니다.

## V40.1 · 설교 작성 전 고정 본문 해석 흐름

FIXED8은 실제 설교를 쓰기 전에 `개역개정 → 히브리어/헬라어 원문 → ESV/NASB → NIV/CSB → NET 번역주석 → NLT 쉬운 표현 → 주석·신앙고백 문서 → 설교 작성` 순서로 근거를 검토합니다. 통합 근거 패킷 대시보드에서 여덟 단계의 준비 여부와 실제 등록 자료명을 확인할 수 있습니다.

이 흐름은 번역본을 기계적으로 나열하라는 뜻이 아닙니다. LM Studio에는 원어 핵심어, 직역 계열의 표현 차이, 의미 중심 번역의 전달 방식, NET의 등록 번역주석 쟁점, NLT의 쉬운 표현을 차례로 검토한 뒤 설교자가 이해하기 쉬운 하나의 설명으로 종합하도록 지시합니다. 저작권 또는 사용권 때문에 해당 번역이 DB에 없으면 모델의 기억으로 채우지 않고 그 단계를 건너뜁니다. 개역개정·ESV·NASB·NIV·CSB·NET·NLT 본문과 NET 주석은 패키지에 포함하지 않으며, 사용자가 정식 사용 허가를 확인한 자료만 로컬 DB에 등록해야 합니다.

### V40 실행기 보정 · 구버전 서버 자동 교체

Windows에서 V38 같은 구버전 서버 창이 아직 포트 8000을 사용하면 브라우저 새로고침만으로는 V40으로 바뀌지 않습니다. V40 실행기는 `/api/runtime`으로 실제 설교 서버임을 확인하고, 포트 8000의 단일 프로세스가 허용된 설교 서버 프로세스이며 실행 버전이 V40보다 **낮을 때만** 그 구버전을 종료하고 V40을 시작합니다. 일반 프로그램이나 판별 불가 프로세스는 종료하지 않으며, V40보다 높은 버전이 실행 중이면 다운그레이드를 차단합니다. 이 처리로 이전 서버 창을 놓쳐 계속 V38 화면이 열리는 문제를 방지합니다.

V40 수정 배포본은 루트의 `VERSION.txt`와 `RUN_V40.bat`으로 다운로드/압축해제 폴더 자체도 검증합니다. FIXED12의 내부 패치 버전은 `40.5.0`입니다. `RUN_V40.bat`은 패키지 표시를 먼저 확인하고, `start.bat`은 `verify_version.py`를 실행해 실제 Python 애플리케이션의 `APP_VERSION`도 다시 확인합니다. Windows `cmd.exe`의 중첩 따옴표/`for /f` 명령 치환을 사용하지 않으므로 경로에 공백이 있어도 버전 확인 명령이 깨지지 않습니다. 따라서 V38 파일이나 이전 V40 수정본을 잘못 실행하거나 서로 다른 버전 파일이 한 폴더에 섞이면 서버를 띄우지 않고 어떤 버전이 잘못되었는지 표시합니다.

`start.bat`은 요구사항 파일의 SHA-256 지문과 필수 모듈을 확인합니다. 첫 실행이나 요구사항 변경 때만 pip 설치를 수행하고, 이후 실행에서는 설치 단계를 건너뛰므로 시작이 빨라지고 반복되는 pip 안내가 줄어듭니다. ZIP 실행본의 데이터는 해당 프로그램 폴더에 있으므로 새 폴더의 수정본으로 이동하기 전 웹 화면의 **통합 백업 만들기**로 백업 ZIP을 내려받아 새 버전에서 복원하세요. 단일 EXE 배포본은 `%LOCALAPPDATA%\SermonLMStudio`를 공용 데이터 위치로 사용합니다.

## V40 · 원어 가져오기 후 본문 연결상태 자동검증

V40은 V39의 OSHB 전체 ZIP 가져오기를 실제 설교 준비 흐름과 연결합니다. **원어 연결상태 점검**에서 선택한 중심본문의 전체 절 수, 원어 근거가 연결된 절 수와 비율, 원어 항목 수, 뜻/음역 보강 수, 출처 수와 누락 절을 확인할 수 있습니다. OSHB/MorphGNT를 등록한 뒤 실제 중심본문에 연결되지 않은 상태를 단순 “등록 성공”으로 오인하지 않도록 했습니다.

### V40 수정본 · 원어 근거/뜻 사전 역할 유지와 공식 Strong XML

`61-Mt-morphgnt.txt` 같은 MorphGNT 파일을 아래 **원어 사전** 영역에서 잘못 선택해도, 한 번 판별된 “원어 근거” 역할을 이후 미리보기에서도 유지합니다. 따라서 같은 파일을 다시 뜻 사전 변환기로 보내 `language·lemma·gloss` 오류를 중복 표시하지 않으며, 위 **원어 근거 파일 일괄 가져오기**의 검사·등록 흐름으로 안내합니다.

뜻/음역 사전에는 기존 JSON/CSV/TSV 외에 MorphGNT의 `strongsgreek.xml`과 Open Scriptures의 `HebrewStrong.xml`을 직접 사용할 수 있습니다. 헬라어는 XML의 실제 Greek lemma와 음역을 MorphGNT lemma에 연결하고, 유니코드 악센트 조합 차이를 정규화합니다. 히브리어·아람어는 `H7225`, `7225`, `c/7225` 같은 Strong 계열 키를 연결합니다. 두 Strong 자료의 뜻은 영어이며, 한글 뜻이 필요하면 사용권을 확인한 한글 사전을 공통 CSV 형식으로 별도 등록해야 합니다.

FIXED7은 두 개의 비슷한 가져오기 화면을 기본 화면에서 분리했습니다. **원어 자료 간편 등록**에서 파일 하나만 선택하면 파일명과 내부 구조를 함께 검사하여 원문 근거 DB 또는 뜻/음역 사전 DB를 자동으로 결정합니다. 권장 출처·사용조건을 채우고 `파일 선택·확인 → 출처·사용조건 확인 → 내 PC DB 등록`의 세 단계만 표시합니다. 수동 단어 입력과 파일 형식 직접 지정은 삭제하지 않고 접힌 **고급 기능**으로 이동했습니다.

또한 브라우저가 자동 선택한 `strongs_greek_xml`과 `hebrew_strongs_xml` 값을 서버 요청 모델도 허용하도록 규격을 통일했습니다. `HebrewStrong.xml` 파일명은 내용에 OSHB와 같은 네임스페이스 문구가 있더라도 히브리어 뜻 사전으로 우선 분류하며, 실제 XML 구조는 변환 단계에서 다시 검증합니다.

또한 V39 화면의 두 구조 불일치를 수정했습니다. 뜻 사전 파일 선택창이 ZIP/XML/TXT를 숨기던 파일 필터를 넓혀 잘못 선택한 MorphGNT/OSHB 자료를 실제로 자동 분류할 수 있게 했고, 구약 OSHB 안내에 남아 있던 “ZIP을 풀고 XML 선택” 문구를 “전체 ZIP 그대로 선택”으로 통일했습니다. 뜻 사전 자체는 계속 JSON/CSV/TSV의 `language, lemma, gloss` 구조만 DB에 저장합니다.

## V39 · OSHB 전체 ZIP 직접 가져오기

V39은 `OSHB-v.2.2.zip` 같은 MorphHB/OSHB 전체 배포 ZIP을 **뜻/음역 사전**으로 잘못 선택했을 때 발생하던 `language, lemma, gloss` 오류를 해결합니다. 이 ZIP은 뜻 사전이 아니라 히브리어/아람어 원문 lemma·형태론 자료이므로 사전 DB에 넣지 않고 **원어 근거 가져오기 → OSHB 전체 ZIP** 경로로 자동 전달합니다. 사용자가 ZIP을 수동으로 풀 필요가 없습니다.

서버는 ZIP 경로 탈출, 암호화 항목, 중복 파일명, 파일 개수, 총 압축해제 크기와 비정상 압축률을 먼저 검사하고 `wlc/*.xml` 성경책만 처리합니다. 전체 구약 원어 데이터를 브라우저 JSON으로 펼치지 않고 미리보기에는 책별 건수와 소량 샘플만 보내며, 실제 등록은 로컬 서버에서 책별 배치로 한 트랜잭션 안에 수행합니다. 재등록 시 기존 행은 건너뜁니다. 출처와 사용조건 확인은 사용자 확인이 필요한 항목이므로 자동 승인하지 않습니다.

OSHB ZIP에는 일반적으로 lemma의 **한국어 뜻/음역 사전 데이터가 포함된 것이 아닙니다**. 뜻·음역 보강이 필요하면 별도로 사용권을 확인한 JSON/CSV/TSV 사전(`language, lemma, gloss`, 선택 `transliteration`)을 뜻 사전 영역에 등록해야 합니다.

## V38 · 원어 자료 역할 자동분류

V38은 `61-Mt-morphgnt.txt` 같은 MorphGNT 형태론/lemma 파일을 **뜻 사전** 입력칸에 잘못 넣었을 때 `language, lemma, gloss` 오류로 끝나던 흐름을 수정합니다. 파일 앞부분의 실제 구조를 검사하여 MorphGNT, OSHB 원어 자료, 원어 근거 표, lemma 뜻 사전 후보를 먼저 구분합니다.

MorphGNT/OSHB 파일을 뜻 사전 칸에 잘못 선택하면 사전 DB에는 넣지 않고 위의 **원어 근거 파일 일괄 가져오기** 흐름으로 자동 전달하여 미리보기합니다. 브라우저 보안상 파일 경로 자체를 다른 `<input>`에 복사하지 않고 이미 사용자가 선택한 `File` 객체만 메모리에서 전달합니다. 서버도 선택된 드롭다운 값과 무관하게 내용 구조를 다시 검사하므로, `TSV`로 잘못 지정해도 MorphGNT를 사전으로 오인하지 않습니다. 출처·사용조건 확인 체크는 사용자 확인이 필요한 항목이므로 자동으로 켜지지 않습니다.

SBLGNT 프리셋을 선택하면 파일 형식도 SBLGNT 공식 XML로 자동 설정합니다. 마태복음은 공식 소스의 `data/sblgnt/xml/Matt.xml`, 신약 전체는 같은 폴더의 `sblgnt.xml`을 사용할 수 있습니다. `LexicalIndex.xml`처럼 구절 경계가 없는 어휘 색인 XML은 성경 본문 DB에 넣지 않고, 왜 사용할 수 없는지와 올바른 파일명을 화면에 안내합니다.

## V33 · 원어 lemma 뜻·음역 사전 보강

V33은 MorphGNT/OSHB에서 가져온 **원문 형태론 근거**와 사용자가 사용권을 확인한 **원어 사전**을 별도 테이블로 관리합니다. 원문 근거의 lemma에 뜻이나 음역이 비어 있을 때만 사전의 정확히 대응되는 항목으로 보강하며, 이미 사람이 검토해 입력한 뜻·음역은 덮어쓰지 않습니다. 원문 출처/사용조건과 사전 출처/사용조건도 별도로 보존하여 설교 근거와 화면에서 함께 확인할 수 있습니다.

원어 사전 파일은 JSON/CSV/TSV를 지원합니다. 필수 열은 `language, lemma, gloss`, 선택 열은 `transliteration`입니다. 헬라어는 MorphGNT lemma 철자를 기준으로 연결하고, 히브리어 Strong 계열 키는 `7225`, `H7225`, `c/7225` 같은 표기를 보수적으로 같은 키로 정규화합니다. 사전 본문은 라이선스 문제 때문에 프로그램이 인터넷에서 자동 수집하거나 번들하지 않습니다. 사용자가 출처와 사용조건을 확인하고 화면의 **원어 사전 · lemma 뜻/음역 연결**에서 검사·등록해야 합니다.

## V32 · LM Studio 8K Context 초과 자동 안전화

V32는 원어·번역·교리 자료가 늘어난 뒤 `request (...) exceeds the available context size (8192 tokens)`로 구조 생성이 중단되는 문제를 수정합니다. 3대지 구조 생성은 중심본문 각 절에 근거가 고르게 남도록 번역/문맥/원어 항목을 프롬프트 전용으로 축약하며, DB의 전체 원자료는 삭제하거나 변경하지 않습니다. 그래도 LM Studio가 context 초과를 반환하면 더 작은 비상 8K 근거 패킷으로 한 번 자동 재시도합니다. 최종 설교 생성과 분량 재조정도 성경·원어·교리 프롬프트 예산을 제한하여 같은 오류의 재발 가능성을 낮춥니다.

LM Studio HTTP 400의 `n_prompt_tokens`와 `n_ctx`도 해석하여 원시 JSON 대신 이해하기 쉬운 한글 context 오류를 표시합니다. 더 긴 본문이나 매우 작은 context 설정에서 비상 모드까지 초과할 경우에는 LM Studio에서 모델의 Context Length를 늘려 다시 로드해야 합니다.

V31은 기존 JSON/CSV/TSV 원어 근거 가져오기에 더해 MorphGNT SBLGNT의 책별 `*-morphgnt.txt`와 Open Scriptures Hebrew Bible(OSHB)의 `wlc/*.xml` OSIS 파일을 직접 검사·변환합니다. V30은 성경 참조에 따라 구약은 히브리어(`he`), 신약은 헬라어(`grc`)를 기본 선택합니다. `Matt 14:27-31` 같은 범위는 원어 근거 조회에는 사용할 수 있지만 직접 lemma를 추가할 때는 `MAT 14:27` 같은 한 절을 요구합니다. 서버와 원어 파일 미리보기에서도 신약을 히브리어, 구약을 헬라어로 잘못 등록하는 명백한 언어 불일치를 차단합니다. 단, 다니엘·에스라 등의 아람어 자료처럼 별도의 학술 언어 코드가 필요한 자료는 허용합니다.

## V29 · WEB 전체 USFM 가져오기 안정화

V29은 eBible `engwebp_usfm.zip`처럼 3만 구절 이상의 USFM을 가져올 때 발생하던 `등록 중단 · ... · Failed to fetch` 문제를 수정합니다. 서버는 구절마다 SQLite 연결/commit을 반복하지 않고 **한 배치당 단일 트랜잭션**으로 처리하며, 브라우저는 로컬 서버 응답이 일시적으로 끊기면 같은 배치를 최대 4회 자동 재시도합니다. `(translation, reference)` UNIQUE 키를 사용하는 upsert이므로 이미 20,000건 등이 저장된 상태에서 전체 가져오기를 다시 실행해도 중복 구절이 만들어지지 않습니다.

또한 eBible USFM의 `\\strong="H..."` 표식과 표준 `\\w ...|strong="..."\\w*` 속성이 일반 성경 본문에 섞이지 않도록 변환기를 수정했습니다. Strong 번호가 필요한 원어 분석은 별도 원어 근거 DB를 사용하고, 성경 본문 DB에는 사람이 읽는 본문만 저장합니다.

V17은 Windows에서 이전 버전의 설교 서버가 포트 8000을 잡고 있을 때의 실행 흐름을 안전하게 개선했습니다. `start.bat`과 EXE가 모두 `launcher.py`를 사용하며, `/api/runtime` 응답이 실제 설교 서버인지 확인하고 포트 8000의 단일 PID와 프로세스 이름까지 검증한 뒤 사용자에게 `[y/N]` 확인을 받습니다. 사용자가 `y`를 입력한 경우에만 그 PID를 종료합니다. 검증되지 않은 다른 프로그램이 포트 8000을 사용하면 자동 종료하지 않습니다. LM Studio의 포트 12345는 이 처리 대상이 아닙니다.

V16은 LM Studio 0.4.20 화면과 로그를 기준으로 연결 계층을 보강했습니다. 인증이 꺼진 로컬 서버에 임의의 Bearer 헤더를 보내지 않으며, 먼저 OpenAI 호환 `GET /v1/models`를 검사합니다. 이 응답이 비정상이지만 LM Studio REST `GET /api/v1/models`가 동작하면 이를 보조 진단 목록으로만 사용하고 화면을 노란색 경고 상태로 표시합니다. 보조목록은 설치된 모델을 포함할 수 있으므로 사용자가 LM Studio의 `Loaded Models`에서 READY인 생성 모델을 직접 선택하게 합니다. 모델명에 embedding/embed 계열 표지가 있으면 임베딩 후보로 분리하여 생성 모델과 RAG 모델 선택란을 구분합니다.

LM Studio 0.4.20 권장 로컬 설정은 `Developer → Local Server`에서 `Server Port=12345`, `Require Authentication=OFF`, `Serve on Local Network=OFF`, `CORS=OFF`입니다. 생성 모델은 `Loaded Models`에서 `READY`인지 확인합니다. RAG를 사용할 때는 생성 모델과 별도로 embedding 모델도 로드합니다. 사용자 화면에서 확인된 `text-embedding-nomic-embed-text-v1.5` 같은 embedding 계열 ID는 임베딩 선택란으로 분리됩니다.

V15는 Windows EXE 배포를 위한 실행 진입점(`launcher.py`)과 `build_windows.bat`을 추가했습니다. EXE에서는 성경 DB·설교 저장본·LM Studio 설정·출력물을 `%LOCALAPPDATA%\SermonLMStudio` 아래에 보존하고, HTML/CSS/폰트 같은 읽기 전용 리소스만 EXE 번들에서 읽습니다. LM Studio API 주소는 화면에서 저장하고 연결 시험할 수 있으며 안전을 위해 이 PC의 `127.0.0.1`/`localhost` 주소만 허용합니다.

V14는 Windows 실행 진단을 개선했습니다. 이전 V13 실행기는 Uvicorn을 별도 창에서 시작한 뒤 짧은 시간 동안 준비 여부만 검사해, 서버 시작이 늦거나 Python import 오류가 발생하면 실제 오류가 가려지고 `server did not become ready`만 보일 수 있었습니다. 이제 `start.bat`이 애플리케이션 import를 먼저 검증하고 Uvicorn을 현재 창에서 직접 실행하므로 실제 오류가 즉시 표시됩니다. 브라우저는 `/api/runtime`에서 실제 V14 서버 응답이 확인된 뒤 자동으로 열립니다.

V13은 첨부 화면에서 설교시간이 `20`만 보였던 혼란을 운영 단계에서 해결합니다. HTML에는 15분이 있었지만 닫힌 `<select>`는 기본 선택값 20만 표시하고 있었습니다. 이제 **기본값 자체가 15분**이며 옵션도 `15분 / 20분 / 25분 / 30분`으로 표시됩니다. 서버의 공식 시간 목록으로 화면을 다시 구성하고 브라우저 캐시를 금지하며, 화면 상단에 실제 실행 버전을 표시합니다.

## V20 · 성경 원본 변환 + DB 관리 + RAG 초기설정

- 공식 설교시간: `15 / 20 / 25 / 30분`
- 기본 설교시간: `15분`
- `/api/runtime`에서 실제 실행 버전, 공식 시간 목록, 기본시간을 확인할 수 있습니다.
- HTML/정적 파일 응답은 `Cache-Control: no-store`로 이전 화면 캐시를 방지합니다.

V12는 V11을 먼저 재점검해 저장본 복원과 화면 순서를 바로잡고, **본문 연구 → 핵심 메시지 → 3대지 구조 → 정확한 시간 배분 → 설교 원고** 흐름을 추가했습니다. LM Studio가 시간을 임의로 합산하지 않고 프로그램이 **15·20·25·30분** 각각의 구간 합계를 정확히 계산합니다. 3대지가 등록되지 않은 성경 참조를 사용하면 원고 생성 전에 차단합니다.

## V12 · 검증된 3대지 구조와 시간 배분

- 화면 순서를 `설교 요청 → 본문 연구 → 원어 확인 → 구조/시간 → 원고/근거 검증 → 저장/승인`으로 정리했습니다.
- 저장 버전을 다시 열면 세부사항, 중심본문, 청중, 신학 전통, 시간, 연구 노트, 설교 구조까지 함께 복원합니다.
- LM Studio가 `핵심 메시지 + 정확히 3개 대지 + 적용 + 예화 방향 + 복음 연결 + 결론 방향`을 JSON으로 제안합니다.
- 각 대지의 성경 참조는 현재 DB에 등록된 중심본문/문맥 근거인지 다시 검사합니다.

- 최종 승인본 ZIP에는 연구 노트가 있으면 `study_note.md`, 설교 구조가 있으면 `sermon_outline.json`도 포함합니다.

300자/분으로 설정한 15분 설교의 기본 배분 예시는 `도입 2 + 본문·문맥 3 + 세 대지 각 2 + 복음 2 + 적용 1 + 결론·기도 1 = 정확히 15분`, 목표 원고 약 4,500자입니다.

## V9 · 실제 설교 준비 운영판

### 개인 낭독속도와 분량조절

- 기본값은 공백 제외 `330자/분`이며 180~600자/분 범위에서 개인 속도를 저장합니다.
- 직접 읽은 80자 이상의 본문과 실제 걸린 초를 입력하면 `글자 수 ÷ 낭독시간`으로 개인 속도를 계산해 저장합니다.
- 설교 생성, 예상시간, 분량 자동보정, 저장 버전 재감사가 모두 같은 개인 속도를 사용합니다.
- 기본 목표시간은 `15 / 20 / 25 / 30분`이며 V13부터 기본 선택은 15분입니다.
- 목표시간과 10% 이상 차이가 나면 LM Studio가 허용된 성경 근거를 유지하면서 최대 2회까지 분량을 다시 조정합니다.
- 최종 Audit에서는 개인 낭독속도 기준 목표시간과 12% 이상 차이가 나면 `needs_review` 경고가 발생합니다.

### 설교 프로젝트 대시보드

저장된 설교를 하나의 프로젝트로 보고 최신 버전 기준으로 `미검토 / 변경 요청 / 승인 / 최종 잠금`, Audit 상태, 목표시간, 예상시간을 한 화면에서 확인합니다. 각 프로젝트에는 예배일, 설교 시리즈, 설교자, 준비메모를 별도로 저장할 수 있습니다.

### 최종 승인본 ZIP

**목회자 승인 → 최종 잠금 → SHA-256 무결성 정상**인 버전만 최종 ZIP 패키지로 만들 수 있습니다.

패키지에는 항상 다음 파일이 포함됩니다.

- `sermon.md` — 최종 설교 원고
- `dashboard.html` — 근거·감사·프로젝트 정보 대시보드
- `sermon.docx` — Word 설교문
- `manifest.json` — 버전, 감사, 잠금, 낭독속도, 프로젝트 및 포함 파일 정보
- `study_note.md` — V11/V12 본문 연구 노트가 저장된 경우 포함
- `sermon_outline.json` — V12 검증 설교 구조가 저장된 경우 포함

나눔글꼴과 WeasyPrint가 정상 준비된 PC에서는 `sermon.pdf`도 함께 포함됩니다. PDF 환경이 준비되지 않았으면 ZIP 전체를 실패시키지 않고 `manifest.json`에 PDF 미포함 이유를 기록합니다.

## V8 · 근거 기반 AI 수정 제안

1. 설교를 생성하고 버전 저장 후 Citation Mapping/Audit을 확인합니다.
2. `근거 확인 필요` 문장이 있으면 **수정 제안 만들기**를 누릅니다.
3. LM Studio에는 해당 문장과 그 버전에 저장된 허용 성경 근거만 전달됩니다.
4. 프로그램은 모델이 반환한 참조가 허용 목록 안에 있는지, 제안문 안에 같은 참조가 실제로 명시되어 있는지 다시 검사합니다. 검증 탈락 제안은 저장하지 않습니다.
5. 화면에서 **수정 전 / 제안문 / 근거 구절 / 제안 이유**를 비교합니다.
6. 필요한 제안만 체크하여 **선택 제안 새 버전에 반영**을 누릅니다.
7. 기존 버전은 변경하지 않고 v2, v3처럼 새 버전을 만든 뒤 Citation Mapping과 Audit을 자동으로 다시 수행합니다.

중요: 이 기능도 성경 구절이 제안문의 신학적 주장 전체를 실제로 지지하는지 의미론적으로 보증하지 않습니다. LM Studio 제안은 반드시 목회자가 원문 성경과 문맥을 직접 확인한 뒤 선택해야 합니다. 승인 또는 최종 잠금된 버전에는 AI 수정 제안을 생성/반영하지 못하도록 차단됩니다.

## V7 Citation Mapping · 재감사 · 최종 잠금

- 설교에서 성경 참조가 명시된 문장을 등록 DB와 연결해 문장 번호와 근거 구절을 표시합니다.
- `성경은 / 본문은 / 말씀은 / 히브리어 / 헬라어 / 원어`처럼 근거가 필요한 표현인데 같은 문장에 확인 가능한 참조가 없으면 **근거 확인 필요**로 표시합니다.
- 근거 확인 필요 항목이 있으면 감사 상태가 `needs_review`가 되어 바로 승인할 수 없습니다.
- 기존 저장 버전은 **선택 버전 재감사**로 현재 원고와 저장된 출처를 다시 검사할 수 있습니다.
- 이미 목회자 승인된 버전은 승인 당시 감사와 현재 감사가 달라지는 것을 막기 위해 재감사할 수 없습니다. 변경이 필요하면 새 버전으로 저장합니다.
- `ready_for_review → 목회자 승인`을 거친 버전만 **승인본 최종 잠금**할 수 있습니다.
- 최종 잠금 시 원고의 SHA-256 해시를 기록하고 조회 시 무결성을 다시 확인합니다. 잠금 뒤에는 해당 버전에 검토 상태 추가나 재감사를 할 수 없습니다.

Citation Mapping은 문장의 신학적 의미가 참인지 판정하는 AI 심사기가 아니라, 명시 참조와 특정 근거 표현을 찾는 **보수적인 검토 보조 기능**입니다. 최종 해석과 설교 적합성 판단은 목회자가 해야 합니다.

## 생성 감사와 목회자 승인

설교 생성 직후 프로그램은 사용한 성경 근거, 원어/교리 출처, DB 미확인 성경 참조, 목표 낭독시간 편차를 기록합니다.

- `ready_for_review`: 자동 점검 경고 없음. **승인을 보장하는 뜻이 아니라 목회자 검토가 가능한 상태**입니다.
- `needs_review`: 미확인 참조, 출처 누락 또는 개인 낭독속도 기준 목표시간 12% 초과 편차가 있어 확인이 필요합니다. 이 상태에서는 승인할 수 없습니다.
- `blocked`: 검색된 성경 근거가 0건입니다. 승인할 수 없습니다.
- 목회자 검토는 `댓글 / 변경 요청 / 승인`으로 버전별 누적됩니다.
- 하나의 생성 감사 기록은 한 설교 버전에만 귀속됩니다. 기존 감사 ID를 새 버전에 재사용하면 자동으로 제거되어 잘못된 승인 근거가 승계되지 않습니다.
- `변경 요청`된 같은 버전은 그대로 승인할 수 없습니다. 수정/재생성한 원고를 새 버전으로 저장하고 새 감사 기록을 거쳐야 합니다.
- 한번 승인된 버전은 후속 판정으로 승인 상태를 되돌릴 수 없습니다. 최종 잠금 전에는 댓글 추가가 가능하고, 최종 잠금 후에는 검토 기록 추가도 차단됩니다.

감사는 출처 존재 여부와 참조 후보를 확인하는 보수적 자동 점검입니다. 성경 해석, 원문 의미, 신학적 타당성 또는 실제 설교 적합성을 자동으로 보증하지 않습니다.

## 로컬 RAG 설정

1. LM Studio에서 설교 생성용 Instruct 모델을 로드합니다.
2. LM Studio에서 별도의 **Text Embedding 모델**도 로드합니다.

LM Studio 공식 Embeddings 문서: https://lmstudio.ai/docs/developer/openai-compat/embeddings

## 1. 준비

1. Python 3.11 이상을 설치합니다. 설치할 때 `Add Python to PATH`를 선택합니다.
2. LM Studio를 설치합니다.

## 2. Windows에서 실행

### 일반 실행

탐색기에서 `start.bat`을 더블클릭합니다. 최초 실행에는 Python 패키지 설치 시간이 걸립니다. 이후 브라우저에서 다음 주소가 열립니다.

`http://127.0.0.1:8000`

상단에 **연결됨**과 LM Studio 모델 이름이 표시되면 준비가 끝났습니다.

### Windows EXE 만들기

Windows 10/11에서 `build_windows.bat`을 더블클릭하면 별도의 `.build-venv`를 만든 뒤 PyInstaller로 `dist\SermonLMStudio.exe`를 생성합니다. EXE 빌드는 운영체제별 네이티브 구성요소가 포함되므로 **Windows에서 Windows용 EXE를 빌드해야 합니다.** 만들어진 EXE는 Python을 별도로 실행하지 않고 사용할 수 있습니다.

EXE 사용 순서:

1. LM Studio를 실행하고 생성용 Instruct 모델을 로드합니다.
2. LM Studio의 Developer / Local Server를 시작합니다.
3. `SermonLMStudio.exe`를 더블클릭합니다.
4. 브라우저가 열리면 `LM Studio 로컬 연결`에서 `http://127.0.0.1:12345/v1`을 확인하고 **저장 · 연결 시험**을 누릅니다.
5. `연결 성공 · 모델 N개`가 표시되면 생성 모델을 선택합니다.
6. 설교시간은 `15 / 20 / 25 / 30분` 중 선택하며 기본값은 **15분**입니다.

EXE에서 사용자 DB와 설정은 `%LOCALAPPDATA%\SermonLMStudio\data`, 출력 파일은 `%LOCALAPPDATA%\SermonLMStudio\exports`, 추가 글꼴은 `%LOCALAPPDATA%\SermonLMStudio\fonts`에 저장됩니다. EXE를 새 버전으로 교체해도 이 폴더의 사용자 데이터는 유지됩니다. `NanumSquareR.ttf`, `NanumSquareB.ttf`, `NanumGothic.ttf`, `NanumGothicBold.ttf` 등을 사용자 fonts 폴더에 넣으면 EXE를 다시 빌드하지 않고 PDF 출력에서 사용할 수 있습니다.

## 3. 성경 자료 준비와 일괄 Import

패키지에는 개역개정이나 쉬운성경 등 사용허가가 필요한 번역의 본문을 임의로 포함하지 않았습니다. 화면 아래의 **성경 자료 추가 → 성경 DB 가져오기 마법사**에서 합법적으로 사용할 수 있는 자료를 넣어 사용합니다.

V26 GUI 프리셋은 `WEB / WLC / SBLGNT / 정식 사용 허가를 받은 사용자 자료`입니다. 공개자료는 서버가 번역명·언어·사용조건·공식 출처를 고정하여 기록합니다. 사용자 허가자료는 **번역본 사용권 등록부**에 같은 번역명을 먼저 등록하고 `전문 DB 저장 허용`을 켠 경우에만 마법사 Import가 허용됩니다.

원본 변환기는 다음 형식을 지원합니다.

- JSON: `reference + text` 또는 `book + chapter + verse + text`
- CSV/TSV: 첫 행에 위 필드명을 헤더로 사용
- USFM: `\\id`, `\\c`, `\\v` 구조
- OSIS/XML: `verse` 요소의 `osisID`를 참조로 변환

변환은 인터넷 서비스로 전송하지 않고 이 프로그램의 로컬 서버에서 처리합니다. 최대 파일 크기는 50MB, 한 번의 변환은 최대 100,000건입니다.

필수 필드:

- 번역/자료명: `WEB`, `WLC`, `SBLGNT`, `개역개정-정식허가본` 등
- 언어: `ko`, `en`, `he`, `grc` 등
- 성경 참조: 한 가지 표기법을 일관되게 사용하는 것을 권장
- 본문/원어 자료: 실제 텍스트
- 사용조건: Public Domain, 라이선스명, 사용허가 정보 등

`sample_bible_data.json`은 데이터 모양을 보여주는 예시일 뿐이며 실제 성경 본문이 아닙니다.

많은 구절은 JSON 배열로 만든 뒤 한 번에 등록할 수 있습니다.

```powershell
.venv\Scripts\python.exe import_bible.py my_bible.json
```

공개 데이터의 권장 공식 출처와 라이선스는 `data/PUBLIC_SOURCES.md`에 정리했습니다.

## 4. 설교 생성 흐름

1. 설교 주제와 세부사항을 입력합니다.
2. 가능하면 중심본문을 입력합니다.
3. 프로그램이 SQLite 성경 DB에서 관련 근거를 검색합니다.
4. 검색된 본문만 LM Studio에 근거자료로 제공합니다.
5. 로컬 모델이 설교 초안을 만듭니다.
6. 결과에서 모델, 검색 근거 수, 예상 낭독시간, DB에서 확인되지 않은 참조 수를 표시합니다. 목표시간과 크게 다르면 LM Studio가 근거를 유지하면서 한 차례 자동 보정합니다.
7. **문장별 성경 근거 연결**과 **사용한 성경 근거 보기**를 확인합니다.
8. 생성 감사 상태를 확인하고 버전을 저장한 뒤 목회자 검토 의견과 승인 상태를 기록합니다. 필요한 경우 저장 버전을 재감사합니다.
9. 근거 확인 필요 문장이 있으면 V8 수정 제안을 비교하고 필요한 항목만 새 버전에 반영합니다. 새 버전은 자동 재감사됩니다.
10. 최종 승인 후 승인본을 잠글 수 있습니다.
11. Markdown, 대시보드형 HTML, Word 또는 PDF로 저장할 수 있습니다. HTML/Word/PDF에는 Citation Mapping, 감사/검토 상태와 AI 수정 반영 계보가 함께 표시됩니다.

## 5. 번역본 병렬 비교

성경 참조 표기가 완전히 같은 자료들을 `번역본 병렬 비교`에서 나란히 확인할 수 있습니다. 예를 들어 WEB, 허가된 한국어 번역, WLC, SBLGNT를 동일한 참조 키로 등록하면 비교 카드에 함께 나타납니다.

## 6. 15·20·25·30분 분량에 관하여

V26은 저장된 개인 낭독속도를 사용하며, 초기 기본값은 한국어 공백 제외 약 330자/분입니다. 선택한 시간의 전체 목표 글자 수와 구간별 시간 합계를 프로그램이 계산합니다. 실제 강단의 쉼, 회중 반응, 성경 봉독 시간에 따라 달라질 수 있으므로 예상 시간은 여전히 참고값입니다.

## 7. 현재 V35의 안전장치와 한계

- 성경 직접 인용은 DB에 제공된 문장만 사용하도록 시스템 지시를 적용합니다.
- 결과의 성경 참조를 DB 검색 결과와 대조해 미확인 참조를 표시합니다.
- 이것은 **1차 자동 점검**이며 신학적·문맥적 정확성을 보증하지 않습니다.
- 히브리어/헬라어 자료가 DB에 없으면 원어를 임의로 단정하지 않도록 지시합니다.
- 생성 결과는 반드시 목회자가 최종 검토해야 합니다.
- 의미검색 벡터는 SQLite에 로컬 저장됩니다. 수만 구절 규모에서도 동작하도록 설계했지만, 대규모 자료에서 더 빠른 검색이 필요하면 다음 버전에서 전용 벡터 인덱스로 교체할 수 있습니다.
